# Agent化
- 希望所有人拥有相同的故障排查，日志分析能力，不要有24小时值班！！！！,也作为一个agent搭建的学习与尝试；
- 日常工作中会有很多同事有查询故障码，故障排查，收集反馈问题，日志分析、手术数据统计等需求，其中日志分析、故障码查询、手术数据分析是logtool已经具备的能力；怎么能让用户更新加顺畅的使用这种能力，使用自然语言就使用这种能力，是不是可以形成一个agent

## 整体设计

把agent分为adapter网关层，会话管理、任务管理、Runtime、工具层；子任务

### 状态机
对于agent整体运行上，AgentRuntime 控制状态机来控制一个消息进入agent后的在各层级之间的跳转；
``` mermaid
stateDiagram-v2
    [*] --> received: AgentRequest

    received --> task_resolving: 保存用户消息
    task_resolving --> context_building: 创建/恢复 agent_task + 创建 agent_run

    context_building --> prompt_preparing: ContextEnvelope 构建完成
    prompt_preparing -->  intent_extracting
    intent_extracting --> planning: ContextIntent 生成完成

    planning --> waiting_user_clarification: 需要用户补充信息
    planning --> tool_spec_resolving: 需要获取工具定义
    planning --> tool_executing: 已有完整工具参数
    planning --> answer_generating: 信息足够可回答
    planning --> rejected: 权限不足/策略拒绝

    tool_spec_resolving --> tool_argument_building: ToolSpec 获取完成
    tool_argument_building --> tool_call_validating: 工具参数生成完成

    tool_call_validating --> waiting_user_clarification: 参数缺失
    tool_call_validating --> tool_executing: 参数合法

     tool_executing --> observation_saving: 工具执行完成
    observation_saving --> context_building: 工具结果进入上下文

    answer_generating --> message_persisting: 生成回答
    message_persisting --> completed: 保存 assistant message

    waiting_user_clarification --> [*]: 暂停等待下一条用户消息
    completed --> [*]
    rejected --> [*]
    failed --> [*]
```

## 网关层 `adapters`
- 用于渠道接入，将各平台的信息都转化为结构化数据，产出标准 [[多轮会话涉及的结构化数据#Agent网关层| #AgentRequest ]] ，
- [[多轮会话涉及的结构化数据#钉钉返回的原生结构化数据|钉钉的原生返回值]]，接入钉钉机器人，需要将原生返回值映射到标准化的 [[多轮会话涉及的结构化数据#Agent网关层| #AgentRequest ]] 
- [[多轮会话涉及的结构化数据#Agent网关层| #AgentRequest ]] 标准化的数据 映射到 [[多轮会话涉及的结构化数据#写入消息的中间映射层| #ConversationMessageInput]] 存入 #conversation_messages 表；
- 对于原生的Web端的 #AgentRequest 结构化数据中的部分字段定义
	- message_id使用 ULID 生成：*ULID是前 10 位字符：时间部分（毫秒时间戳编码） 后 16 位字符：随机部分（高熵随机）*；每一个消息固定一个ID；
	- request_id使用 UUIDv4生成，一次http请求一个ID，多次请求可以是一个message_id，因为消息可以重发，就产生多次请求，但内容是同一个id；*UUIDv4 是一种通用唯一标识符格式（128位），基于随机数生成。常见形态：xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx（36字符，含连字符）。*
	- traced_id一条业务链路的追踪ID（用于全链路日志排障）使用 UUIDv4生成；
- 非原生的消息使用平台传入的ID，==是否需要考虑限制和约束==；
- 这一层只是做消息的接收；

## 会话管理 `orchestrator`

- adapter层接入的是消息，当触发了 #AgentRequest 请求后，开始构建会话，
- 三层架构：会话容器(Container) -> 会话实例(Instance) -> 消息(Message)。
	- Adapter 只负责把平台消息标准化为 #AgentRequest ，会话归属与切分在统一会话层处理。
	- Web 与或其他平台使用同一规则：container_key 稳定归属，instance 负责当前会话上下文轮次。
	- 会话切分统一触发：新建会话、达到 20 轮、空闲超过 30 分钟、token超过阈值；
- 标识规则：
	- container_key = channel_type + user_id + conversation_id，通过此key字段可以确定会话容器的归属，没有就新建
		- 其中conversation_id 存 adapter 原始值（钉钉来自平台，Web 由新建会话生成）
			- Web（原生）新建一次对话 -> 新的 conversation_id，同一对话内多轮消息 -> 复用同一个 conversation_id
			- 钉钉一般用钉钉回调里的 conversationId（群聊/单聊会话标识），同一个聊天窗口（同一会话）消息通常复用该 ID，换群/换单聊对象/新会话空间 -> conversation_id 变化
		- container_key 来定位 #conversation_containers ，通过container_id定位到目前激活的实例 #conversation_instances ，一个会话容器中只存在一个激活的会话实例，没有就新建，以此可以定位到对应的 #conversation_messages 实例和消息是一对多的关系；
- 数据模型：
      - conversation_container：归属元数据（平台/用户/conversation_id/container_key）
      - conversation_instance：会话状态（active/archived、turn_count、last_message_at、version
      - conversation_message：消息事件，需要支持附件，可以先预留（role/content/payload/requestId/messageId/traceId）
  - 会话层的核心流程：
      - 入站消息 -> adapter 标准化，agentRequest -> 定位容器 -> 选 active 实例（必要时新建 -> 构建上下文（最近窗口）-> 写消息
  - 幂等与并发：
      - 消息的幂等键：channel_type + user_id + conversation_id + message_id
      - 队列按 conversation_instances.id 分区串行消费（实例内串行，实例间并行）
      - 队列是使用redis，专用的会话队队
- 会话构建， 收到 #AgentRequest 请求后，通过container_key来确定会话容器并找到激活中的会话实列若无激活中的会话实例则新建，根据实例可以查询到该实例下的历史消息 #conversation_messages ，由 #AgentRequest 和历史消息构建 [[多轮会话涉及的结构化数据#^d1e9a8| #ContextEnvelope]] -> 给到意图识别层；
- 这里的 #ContextIntent 是不是只应该包含以下这些内容：用户本轮的问题、历史会话的上下文、已经明确的信息；
	- 对于 #contextenvelope 定义与解释
		-  #rawText 记录的是当前的问题，完整记录用户当前的问题；
		- #fileIds 是用户本轮或历史上下文中上传/引用的附件 ID 列表
		- #historySummary  包含三个字段，lastTool上一轮使用的工具、lastResultBrief上一轮的结果，通过意图识别时同步通过LLM总结；lastIntent是上一轮的意图，这些都是通过LLM返回结果才能获得的；
		- #recentTurns 从该会话中获取前X轮对话的问题、回答、意图识别的结果，其中role定义为三类是用户问题user、Intent & Fact Extractor 结果intent、LLM的回答assistant
		- text内填写对应的内容，完整填写不需要总结；
		- turn填写轮次，上X轮=X，上一轮=1，目前可以按照X=2实现；
		- #confirmedSlots 这一步部分也是根据LLM获得的，
		- #contextVersion 版本号，用于记录 #contextenvelope 的版本变化
- 输入给LLM做意图识别前需要把结构化的 #contextenvelope 转化为自然语言的prompt，这一步可能是拼接的，然后再输出到LLM，但需要保证返回的是结构化数据

## 利用大语言模型的编排与构建 `LLM Orchestrator & Extractor`
- 对于提示词构建应该分为几个部分， #contextenvelope 主要用来管理用户的会话历史上下文， #contextTool 主要用来构建工具部分的prompt；
- 通过 #contextenvelope 转化为自然语言的prompt[^2]，提示词需要包含system、user、tool、memory这几部分
	- system包含定义agent的形式，需要解决什么问题，限制LLM的返回的结构化输出的内容和填写规则；
	- user部分包含用户的输入和上下文；
	- tool部分包含可以使用的现有工具与摘要；
	- memory暂时未填写；
- prompt根据系统语言区分中文和英文；
- prompt按照配置的方式实现，prompt调用 #LLM 得到意图和事实澄清的结果，规范 #LLM 填写一个结构化的数据 [[多轮会话涉及的结构化数据#意图识别结果| #ContexIntent]]，意图识别的结果需要转化映射到 [[多轮会话涉及的结构化数据#写入消息的中间映射层| #ConversationMessageInput]] 做标准化，然后通过message service存入 #conversation_messages 表，这部分仅用于记录原生的 #LLM 的返回内容；以role = assistant 写入数据表

## 规划层 Planner  
- 需要根据 #ContextIntent 、上下文、工具权限、整体策略构建 #planInputContext 
	- 其中 requestMate 需要根据会话确定traceId、requestId、sessionId、turnId；
	- contextIntent 根据 校验过后的内容 直接映射；
	- contextSummary 根据本次会话构建时的 #contextenvelope 一一映射；
	- availableTools 里放“已注册工具 + 该工具所需权限/约束”；
		- name工具名称、enabled是否启用、requiredPermission需要的权限、allowed（基于当前用户权限计算）
		- requiredSlots 需要的输入参数，不同的工具需要有不同的输入内容；
		- runtimeState 运行状态字段
			- userPermissions 来自鉴权结果；再按工具相关权限做裁剪
			-  remainingCalls 工具调用预算剩余次数
			-  resetAt 限流/配额窗口重置时间
		- policy字段
			- maxSteps单次计划最多允许多少个步骤。
			- maxToolCalls单次计划最多允许调用多少次工具。
			- timeoutBudgetMs单次计划可消耗的总时间预算（毫秒），超出就降级。
			- clarifyRoundLimit最多允许连续追问用户几轮，超过后应改为其他处理（如给保守答复或结束本轮）。
## 消息服务层 Message Service
- 消息层存入消息表时需要标准化数据结构 #ConversationMessageInput 
	- 其中role用来区分消息的来源，仅有 user、assistant、tool、system，user是用户的消息，assistant是LLM返回的消息，tool是使用工具的结果，system是系统返回的消息可以用来处理异常和预设命令；
	- message type用来区分消息类型，比如assistant中的`LLM Orchestrator & Extractor`的返回值属于intent_result，tool返回的是tool_result，用户的纯文字输入时text，如果带有附件的输入是mixed
	- adapters 层收到的用户消息，需要转化为 #AgentRequest , #AgentRequest 映射为 #ConversationMessageInput 再存入消息数据表；
