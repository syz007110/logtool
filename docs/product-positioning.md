# logtool 产品定位

logtool 是面向腹腔镜手术机器人的**设备工程分析能力平台**。  
它把设备日志、手术运行数据和工程词典变成可调用的分析能力，再通过对话 Agent、企业钉钉和 MCP 送到工程师手里。

它不是大而全的后台管理系统。用户/角色、反馈工单、知识库 CMS、配置页可以继续存在，但它们是控制面，不是产品。

## 一句话

**分析能力在内，便捷入口在外：日志分析、手术分析，以及后续的故障诊断与寿命预测；用 MCP 暴露能力，用一个 Agent 执行，用钉钉作为企业内最轻的入口。**

## 是什么 / 不是什么

| 是 | 不是 |
|---|---|
| 设备工程分析平台 | 运维/行政后台、通用 CMS |
| 日志与手术数据的解析、检索、统计、可视化 | 以 CRUD 页面堆功能的管理系统 |
| 可被 Agent / 外部工具调用的能力面 | 多 Agent 编排框架或聊天机器人产品 |
| 钉钉作为一个渠道适配器 | 钉钉小程序或又一套管理后台 |
| 故障码、设备主数据作为分析上下文 | 以故障码/案例/知识库维护为中心的内容管理系统 |

## 产品结构

```text
入口层（薄）
  钉钉对话  ·  Web 分析工作台  ·  MCP（IDE / 外部 Agent / 自动化）
        │
        ▼
运行时（一个 Agent）
  意图 → 规划 → 调工具 → 回写 ToolResult → 再规划 → 回复
        │
        ▼
能力契约（同一份工具目录）
  内部 Agent 工具注册表  =  对外 MCP tools
        │
        ├── 日志分析          （现在）
        ├── 手术分析          （现在）
        ├── 故障诊断          （近期：从「查码/管案例」提升为诊断能力）
        └── 寿命预测          （未来）
        │
支撑面（控制面，维持可用，不作为建设重点）
  鉴权与权限 · 设备/系列主数据 · 故障码词典 · 任务队列 · 审计
```

三层职责：

1. **领域能力**：真正产生工程判断的模块（解析、分析、诊断、预测）。
2. **能力契约**：MCP / Agent 工具目录，是唯一对外能力表面。
3. **入口**：钉钉、Web 工作台、MCP 客户端。入口不拥有业务，只投递请求和呈现结果。

## 领域能力

### 现在：日志分析

设备日志的上传、解密/解析、检索、批量分析、统计与可视化。  
这是系统已经具备、且必须继续做深的主能力。工作台形态保留（如批量分析页），同时必须变成可被 Agent / MCP 调用的工具，而不是只能在后台点选。

### 现在：手术分析

手术记录、按设备/时间的统计、可视化与导出。  
与日志分析并列，不从属于「日志菜单下的一个子页」。运行数据解析与手术分析按设备系列走独立策略，互不回落。

### 近期：故障诊断

今天故障码、故障案例、知识库主要停在「数据管理」：维护、检索、导出。  
目标是把它们收成诊断能力：给定日志/报警/故障码/设备上下文，给出有证据的工程判断（原因、相关参数、历史相似问题），而不是再做一个案例库后台。

现有 `error_code_lookup`、`device_context_lookup` 是起点，不是终点。

### 未来：寿命预测

在日志、运动数据、手术负荷之上做部件/整机寿命与耗损相关预测。  
未落地前不预建页面、不预建数据模型膨胀；等信号与算法边界清楚后再作为独立领域模块进入能力目录。

## 能力契约：MCP

MCP 是 logtool 对外的**工具合同**，不是新的产品线。

原则：

- **一份目录**。内部 Agent 的 tool registry 与 MCP tools 同源。禁止维护两套 schema、两套权限、两套审计。
- **只暴露领域能力**。日志分析、手术查询/分析、故障码与设备上下文、后续诊断与预测。不把用户、角色、配置、反馈、知识库 CMS 做成 MCP 工具。
- **权限与 API 一致**。MCP 调用走既有鉴权与权限点；身份来自调用方凭证，不另开旁路。钉钉渠道的 `permissionBypassChannels` 是渠道特例，不扩散到 MCP。
- **结果可审计、可回放**。工具入参、出参、traceId 可追踪；Agent 会话里已有的 ToolResult 回写路径保持不变。

当前内部工具（`error_code_lookup`、`device_context_lookup`、`start_log_upload`）应视为 MCP 目录的第一批成员。缺口按领域补：日志查询/分析、手术分析，然后才是诊断与预测。

## 运行时：一个 Agent

保留现有单一编排壳（`taskGateway` / turnLoop），不推进多 Agent 平台。

路径不变：意图 → 规划 → 工具执行 → 将 ToolResult 写入消息 → 再构建上下文并规划，直到 `reply_direct` 再持久化助手消息。默认同步，超时自动异步。

Agent 的价值是把领域工具串成对话，而不是再长一层「智能搜索产品」。Web 智能搜索入口与钉钉共用这一运行时。

## 入口

| 入口 | 角色 | 不做 |
|---|---|---|
| **企业钉钉** | 工程师最轻的问询入口：查故障码、丢日志、问某台设备/某场手术 | 不在钉钉里做管理后台、不做选模型 UI、渠道限制（如视频）只留在适配器 |
| **Web 分析工作台** | 深度分析：日志批分析、手术统计/可视化、对话排查 | 不再把侧栏做成「数据管理 + 系统管理」门户 |
| **MCP** | 给 Cursor / 其他 Agent / 内部自动化直接调能力 | 不把 MCP 做成通用数据库或文件访问代理 |

钉钉已有 `dingtalk_stream` 长连接与 `sessionWebhook` 回推，继续作为渠道适配器演进即可。

## 对现有系统的态度

现网已经长成「综合后台」：故障码/i18n 维护、案例库、知识库、反馈、用户角色、监控看板、配置管理。这些代码不要求立刻拆除。

执行纪律：

- **领域能力优先增长**：日志分析、手术分析、Agent 工具、MCP、钉钉入站/出站。
- **控制面冻结扩张**：用户/角色/反馈/知识库 CMS/案例流转/配置页，只在领域能力被堵住时才改。
- **新功能先问入口**：默认应能被 Agent/MCP 调用；只做页面、不能被工具调用的能力，视为没有完成。
- **不把支撑数据当产品**：故障码词典、设备主数据、系列策略是分析上下文，维护界面保持能用即可。

## 变更过滤器

后续需求/PR 用这一条判断：

- 若改动主要是 CRUD、菜单、治理页面、运营配置 → **控制面**。默认不做，除非它在给某个领域工具解阻。
- 若改动是解析/分析/诊断/预测，或 MCP / Agent / 钉钉渠道 → **产品**。可以做。
- 若新页面不能对应到一条（或一组）MCP/Agent 工具 → **先补工具合同，再考虑 UI**。

## 当前与目标的对照

| 层 | 现在 | 目标 |
|---|---|---|
| 自我描述 | 医疗设备/运维综合平台 | 设备工程分析能力平台 |
| 能力中心 | 后台菜单（数据管理 + 系统管理 + 日志） | 日志分析、手术分析，再扩展诊断与预测 |
| 对外合同 | REST + 少量 Agent 工具 | 同一份工具目录，同时服务 Agent 与 MCP |
| Agent | 作为智能搜索壳，工具很少 | 运行时；工具覆盖主领域能力 |
| 钉钉 | 已接入的渠道 | 企业内默认便捷入口，不长业务 |
| Web | Dashboard 门户 | 分析工作台 + 对话；管理功能退到支撑 |
| 故障码/案例/KB | 数据管理模块 | 诊断能力的证据源，而不是 CMS |
| 寿命预测 | 无 | 独立领域模块，成熟后再进目录 |
