# 自动上传日志组件需求

**使用 Node.js + Electron 的日志上传客户端**

为现有的logtool项目写一个组件，用于将本地文件夹中的新增日志自动上传至系统；

## **1. 功能目标**

- 运行在 Windows，可快速适配部署于ubantu或linux。
- 监控指定目录（用户可手动添加目录，不超过10个）。
- 监控形式监控指定目录的新增或变更
    - 监控目录下出现新文件夹文件/压缩包
    - 现有文件夹的时间更新
- 支持从文件夹或压缩包的名称中提取设备名称，
- 支持从文件夹或压缩包及其子文件中提取密钥文件systemInfo.txt
- 支持断点续传、失败重试。
- 前端 Vue 界面，提供配置和状态展示。
- 托盘常驻，提供提示/控制。

## **2. 模块划分**

**配置管理模块**

- 可配置的内容包括：
    - 后端的API
    - token（支持自动更新）、token过期时间
    - 用户名、密码
    - 自动登录标志位
    - 并发数
    - 监控目录
    - 监控递归深度
    - 日志文件格式设置（.medbot）、密钥文件格式设置（systeminfo.txt）
    - 只扫描不上传标志位
    - 日志保存路径
    - 扫描模式：只监控新增/变更，启动时扫描现有文件
    - 全量扫描周期：1（min）
    - 临时文件删除周期
- 用户可在 UI 界面配置：
    - 监控路径管理（多个目录可选限制最多10个）上传该日志
    - 启动扫描模式设置；
    - 日志存储路径；
- 配置保存方式：config.json 本地存储，启动时加载。

**目录监听模块**

- 监听逻辑参照 [监听流程图](https://app.notion.com/p/259cc02ebc29801e8c8ccc4e749bbd2c?pvs=21)

**上传任务队列模块**

- 本地使用upload_tasks来维护上传文件上传状态；
- 控制并发（一次只上传 3 个文件，并发数2）；
- 上传使用后端logtool的日志上传接口；
- 失败时：指数退避重试（1min → 5min → 30min）；

**本地存储模块**

- 用于保存上传状态（防止程序重启丢失任务）：
    - 数据库存储方式：better-sqlite
    - 数据库存储路径和日志存储路径一致
- 表结构示例：
    - upload_tasks（任务表）
        
        ```sql
        CREATE TABLE IF NOT EXISTS upload_tasks (
          id INTEGER PRIMARY KEY AUTOINCREMENT,        -- 主键
          device_id TEXT NOT NULL,                     -- 设备编号（从文件夹/文件名中提取）
          file_path TEXT NOT NULL UNIQUE,              -- 文件的完整路径（唯一）
          file_hash TEXT,                              -- 文件内容hash（用于去重校验）
          status TEXT CHECK( status IN ('pending','uploading','success','failed') )
                 DEFAULT 'pending',                    -- 上传状态
          retry_count INTEGER DEFAULT 0,               -- 上传失败重试次数
          last_error TEXT,                             -- 最近一次错误信息
          created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, -- 任务创建时间
          updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        );
        ```
        
        - 上传流程：pending → uploading → success 或 failed
        - 失败重试策略由 retry_count 控制
        - 唯一性通过  file_hash 保证
        - 可以每次程序启动时用恢复任务
        
        ```sql
        UPDATE upload_tasks SET status='pending' WHERE status='uploading';
        ```
        

**UI 界面模块（Vue + Electron 渲染进程）**

- 功能页面：
    - 任务列表显示（显示当前任务状态、成功/失败次数）
    - 配置页（监控目录管理（添加/删除路径、运行日志保存路径）
    - 与logtool的连接状态（已连接？未连接）
    - 启动或暂停日志自动上传功能开关
- 托盘菜单：
    - 显示上传状态（绿色正常、红色失败）
    - 一键暂停/恢复上传
    - 打开配置界面

**系统提示模块**

- 事件通知：
    - 上传成功/失败 → 桌面消息通知
    - 新任务加入队列 →桌面消息通知
- 日志记录：
    - 本地写 client.log，保存运行日志，方便排查。

**安全性**

- 与后端 API 通讯：
    - HTTPS + JWT/Token 鉴权
- 上传数据：
    - 日志文件走 multipart/form-data
    - 携带 device_id、客户端 client_id（唯一标识客户端机器）

# **4. 后端 API 要求**

前端 Electron 客户端调用的接口：

- POST /api/uploadLog
    - 参数：device_id, file, source_type=client
    - 返回：{ success: true, log_id: 123 }
- GET /api/config（可选，用于集中配置下发）

# **5. 优势总结**

✅ 前后端统一技术栈（Vue/Node.js）

✅ Electron 桌面应用，用户体验好（托盘/弹窗/可配置）

✅ chokidar 目录监听，跨平台兼容（Windows/Linux/Mac）

✅ 任务队列 + 本地存储，保证可靠上传

✅ 后端只需要提供接口，逻辑更清晰

文件扫描整体逻辑：
- 输入对象
	输入不是本地目录，而是“本轮用户上传的附件集合”。
	每个附件先归类为：
	普通文件
	压缩包：zip / 7z
	其他白名单文件：.txt
- 单附件展开
	参考 log-monitor 的 scanUnit(unitPath) 思路：
	如果是 zip/7z，先解压到临时目录
	如果不是压缩包，直接作为扫描根
	每个附件都视为一个 scan unit
	这一步建议保留 log-monitor 的行为：
	支持 .zip
	支持 .7z
	解压后再扫描内容
	临时目录不立刻删，等后续上传完成后清理
- 目录扫描
	参考 scanDirectory(...)：
	递归深度限制为 3
	扫描每个文件/目录
	同时维护当前单元里的：候选日志文件
	候选密钥文件
	设备编号线索
-  日志文件识别
	直接参考 log-monitor 的严格规则，不建议放宽：
	扩展名必须是 .medbot
	文件名必须匹配 YYYYMMDDHH_log.medbot
	对应现有逻辑就是 [scanner.js](/D:/code/project/medbot/logtool/clients/log-m5. 密钥文件识别
	第一版建议也直接沿用：
	文件名为 SystemInfo.txt
	从内容里提取 MAC 地址样式密钥
	对应逻辑参考：
	parseKeyInDir(...)
	findUnitKey(...)
- 设备编号识别
	参考 log-monitor 当前策略：
	先从压缩包名/目录名/路径名中提取
	规则优先支持：5G-数字、4xxx-xx、BLockX-XXX，也就是现有 extractDeviceIdFromPath(...) 这类思路。
-  配平优先级
	建议优先级明确成：
	用户显式补充的密钥
	SystemInfo.txt 解析出的密钥
	通过 deviceId 检索到的密钥
	设备编号则是：
	用户文本显式补充的 deviceId
	文件夹名 / 压缩包名 / 路径名抽取
	由密钥反查设备编号
- 去重
	这里也建议参考 log-monitor，但第一版可以简化：
	保留：
	单个扫描单元内同名日志去重
	压缩包展开后与非临时目录同名文件优先非临时目录
	可以先不做：
	桌面端那种基于持久化任务队列的 hash 去重
	跨重启 success-hash 去重
