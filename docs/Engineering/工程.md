## 审计
### 需求
系统需要有审计功能，能够记录用户的操作信息，为了可以记录用户的行为，为后续统计、复盘、问题排查、分析用户行为建立数据基础，记录的信息至少包含 时间戳、故障码、操作人、做了什么事情、结果是什么、事情的概述；
	审计记录支持查询、导出；
	需要有独立的权限：审计记录的查询，审计记录的导出；
	有独立的审计查询、检索页面、导出页面；
		默认按照时间排序展示审计信息
		支持 时间、业务事件码、操作人 作为关键词的检索；
### 技术方案
- 审计是独立的公共基础模块，不依赖具体业务表或业务流程实现；但每个业务功能必须显式定义并调用 AuditService，写入其业务语义事件
- 整个系统统一的审计格式，所有功能写入同一格式，所有事件使用相同的公共字段结构，固定公共字段 + 事件专属 details的 JSON 格式，字段定义基于下表

| 字段              | 对于数据表                                         | 含义                                                                                                                                             |
| :-------------- | :-------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------- |
| 固定公共字段          |                                               |                                                                                                                                                |
| `schemaVersion` | schema_version                                | 审计格式版本，未来格式演进时使用                                                                                                                               |
| `eventId`       | event_id                                      | 审计事件唯一标识，使用 ULID                                                                                                                               |
| `occurredAt`    | occurred_at                                   | 时间戳，服务端产生时间，统一 UTC                                                                                                                             |
| `eventCode`     | event_code                                    | 发生的业务事件，如 `AUTH.LOCAL_LOGIN_FAILED`，必须来自预先定义的事件字典                                                                                              |
| 事件专属details     |                                               |                                                                                                                                                |
| `category`      | category                                      | 根据业务事件获得对应分类，必须来自预先定义的枚举，如 `auth`、`rbac`、`user`、`config`、`data`，                                                                               |
| `outcome`       | outcome                                       | 事件的结果，必须来自预先定义的枚举`SUCCESS`、`DENIED`、`FAILURE`                                                                                                  |
| `reasonCode`    | reason_code                                   | reasonCode 必须符合对应 eventCode 的允许范围拒绝或失败原因码；<br>成功事件的 reasonCode 必须为 null；<br>DENIED 或 FAILURE 事件必须提供符合事件定义的 reasonCode                          |
| `actor`         | actor_type<br>actor_user_id<br>actor_username | 操作者；匿名登录失败时可为空，定时任务使用 `SYSTEM`                                                                                                                 |
| `target`        | target_type<br>target_id                      | 被操作的对象，如用户、角色、配置或业务记录                                                                                                                          |
| `request`       | request_id<br>ip<br>user_agent                | 请求关联信息，用于排查与追踪                                                                                                                                 |
| `details`       | details                                       | details 即使没有业务内容，也由 AuditService 写入空对象 {}；<br>details 出现事件白名单之外的字段时，AuditService 拒绝该审计事件；<br>\|命中全局敏感字段黑名单时，AuditService 脱敏该字段，并写入不含敏感内容的运行告警。 |

- AuditService 统一生成 eventId、occurredAt，并从请求上下文补充 
	actor(type、userId、username)、request（requestId、IP、User-Agent)。业务模块传入：eventCode、outcome、reasonCode、target、details，category 不由业务模块传入，AuditService 自动完成根据 eventCode 获取 category、允许的 outcome、reasonCode、target_type 和 details 白名单；生成 eventId、occurredAt、schemaVersion；补充 actor、request；校验、脱敏并写入 audit_logs（数据库）。
- eventCode、category、outcome、reasonCode 必须来自预先定义的事件字典和枚举；审计事件字典和 details 白名单由后端代码维护，不能通过管理页面动态修改。target_type、actor_type、category、outcome 均为后端维护的有限枚举；
	reasonCode 必须符合对应 eventCode 的允许范围。
	成功事件的 reasonCode 必须为 null；
	DENIED 或 FAILURE 事件必须提供符合事件定义的 reasonCode。
	details 即使没有业务内容，也由 AuditService 写入空对象 {}；
	details 出现事件白名单之外的字段时，AuditService 拒绝该审计事件；命中全局敏感字段黑名单时，AuditService 删除或脱敏该字段，并写入不含敏感内容的运行告警。
- 审计日志自动删除，审计日志默认保留 30 天，保留期限可由受控系统配置（后端env配置）修改。到期日志由独立的审计清理任务按批次自动删除，应用运行账户仅拥有 audit_logs 的 SELECT、INSERT 权限；审计清理任务使用独立的运维/维护数据库账户，仅在 audit_logs 上额外拥有受控的 DELETE 权限。清理任务每次执行后，写入 AUDIT.LOGS_PURGED 审计事件，记录保留期限、清理时间范围、删除数量与执行结果。
- 审计记录不可由普通业务接口修改或删除；不记录密码、Token、验证码、钉钉授权码、完整身份敏感信息；审计记录是追加式数据，业务接口不提供修改或删除能力；应用运行账户：audit_logs 的 SELECT、INSERT，审计清理任务账户：audit_logs 的 SELECT、INSERT、DELETE高风险状态变更应与成功审计记录在同一数据库事务中提交。
- 审计内容最终写入数据库

```SQL
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,

  event_id CHAR(26) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
```

## 角色权限
### 需求
- 系统应该有初始角色，超级管理员和普通用户，系统角色不能删除；超级管理员应该拥有所有功能的权限，普通用户仅有被授予的功能权限；
- 一个用户必须拥有至少一个角色，若用户拥有多个角色，那么获得的权限是所有角色的并集，用户可以知道自己是什么角色；
- 角色控制的权限限制的是用户是否可以使用某个功能，不可使用同时也看不到；
- 超级管理员可以创建自定义角色，删除自定义角色，修改自定义角色和普通用户的权限；
	角色的名称是超级管理员可以设置的；

	
### 功能
- 需要有 #用户 - #角色 - #权限  这样形式的模型，每一个用户都有角色，每一种角色都有自己的权限范围
	通过维护数据库表来建立之间的关系

| 表名                | 用途      | 说明                  |
| ----------------- | ------- | ------------------- |
| #users            | 用户表     | 管理用户的数据表            |
| #roles            | 角色表     | 管理角色的数据表            |
| #user_roles       | 用户角色表   | 建立用户和角色之间的关系，多对多的关系 |
| #permissions      | 权限表     | 管理功能权限的数据表          |
| #role_permissions | 角色权限关联表 | 建立角色和权限之间的关系，多对多的关系 |
- 每一个启用的用户必须拥有至少一个有效角色，没有被删除的角色就是有效角色，用户和角色是多对多关系，可以同时拥有多个角色；最终权限取所有有效角色权限的并集。
- 初始化时，通过数据库初始化来完成加载两个系统角色，分别为超级管理员和普通用户
	系统角色的 is_system = true，系统角色无法被角色管理页面删除，同时不允许通过修改其 code、is_system、is_super_admin 和scope_type、scope_id。
		超级管理员角色 is_super_admin=true，其全部权限由后端自动授予，角色权限不可修改，超级管理员角色拥有任何权限，使用is_super_admin进行权限判断；
		普通用户角色的 is_system=true、is_super_admin=false，其角色属性不可修改，但其 role_permissions 可由超级管理员修改
	permissions 是系统维护的功能权限目录；角色管理页面只选择已有权限，不允许超级管理员自行创建任意权限。前端使用树形控件作为展示方式，可以考虑使用 #permission_groups 维护，目前暂时不动；
- 除部署初始化的首个超级管理员，所有自动创建、钉钉首次登录创建、超级管理员创建的普通账户，默认分配普通用户角色。
- 角色管理页面支持角色的增删改查，
	只有超级管理员可以创建自定义角色、分配角色（支持一个用户拥有多种角色）、修改自定义角色和普通用户角色的权限，创建角色的同时可以定义角色的权限；
	角色支持中英文两种语言，通过数据库维护中英文显示的名称
	系统角色（普通用户、超级管理员）不能删除
	删除自定义角色前必须检查是否仍有用户绑定；已分配角色禁止删除
	系统必须始终至少保留一名启用且拥有有效超级管理员角色的用户。若停用用户、删除用户或撤销其超级管理员角色，会导致系统不再存在该用户，则必须拒绝该操作。
	后续超级管理员只能由现有超级管理员向已存在用户分配超级管理员角色产生；不通过普通用户自动创建流程产生。
- 权限目录由系统随功能发布、数据库迁移进行维护；角色管理页面不提供权限项本身的增删改查能力。
- 角色权限控制两个方面:后端强校验；前端再做“可见性/可用性”控制以优化体验。两者都要，且以后端为准。

## 1.1 登入
### 功能
- 登入方式普通用户在全局配置未开启时仅能通过钉钉认证登录，指定超级管理员保留独立的用户名密码应急登录入口，全局配置仅控制普通用户的用户名密码登录，不影响超级管理员入口；限制只能通过钉钉登入是为了限制企业外的用户登入该系统，这样做的目的是用钉钉管理企业用户的方式来限制非企业人员登入；
- 实际实现方式是 钉钉的账户和系统内的账户是两套，钉钉是由钉钉系统定义的账户系统，而logtool内部还是会维护一套账户系统，内核是通过钉钉的账户换取logtool内部账户系统，通过钉钉免密、扫码登入的都会换取logtool内部的一个账户，与钉钉建立一一绑定的关系；
- 普通用户首次钉钉登录时，由数据库自动生成递增的 id；服务端使用 ULID 生成 username，格式为 `dd_ 加随机且不可预测的唯一字符串`，例如 `dd_01K7H9QX4M7J2A8P6R3T`。数据库 `UNIQUE` 约束保证用户名不重复
- 不提供公开注册或自助创建管超级管理员。首个超级管理员由部署初始化创建；后续管理员仅能由超级管理员在系统内授权或通过受控运维流程创建。
- 无注册功能；
- 无忘记密码的功能；
- 已授权钉钉账户指通过钉钉认证后，服务端必须验证用户属于配置的 dingtalk_corp_id 企业
	验证通过后，首次登录自动创建并绑定 Logtool 内部账户；
	已有内部账户时，必须同时满足 is_active=true 才允许登录。
- 保留用户名和密码登入的方式，但通过一个全局配置来开启或关闭这个登入方式；
	前端根据该配置决定是否显示用户名密码登入的方式（控制是否显示）
	后端根据该配置决定是否可以通过用户名或者密码登入（控制是否可以用用户名或密码登入）
	保留独立的管理登入方式（区别于普通登入的入口），仅支持超级管理员角色登入，前端的预留选择入口页面底部小链接的形式（仅超级管理员支持在该入口使用用户名和密码登入，非超级管理员角色不能通过该入口登入）
	用户名密码登入的方式仍旧遵循密码强度要求：长度：≥ 8 位、必须包含：大写字母（A–Z）、小写字母（a–z）、数字（0–9），不允许：与用户名相同、连续相同字符 ≥ 4 个
		连续失败 3 次后，下一次提交开始要求验证码；
		连续失败 5 次，锁定该用户名的本地密码登录 15 分钟；
		独立的登入IP限流，同一 IP：1 分钟内最多提交 20 次登录请求，使用redis计数的方式；
		超级管理员密码锁定不影响其钉钉登录；
		is_active=false 才阻止该账号所有登录方式。
		用户名不能重复；
- 用户登入失败时需要有对应的提示信息	
- 支持语言切换的功能，根据浏览器自动识别语言；
### 数据库
```SQl
CREATE TABLE IF NOT EXISTS users (
  id INT AUTO_INCREMENT PRIMARY KEY,

  username VARCHAR(100) NOT NULL UNIQUE,
  password_hash VARCHAR(255) NULL,
  local_login_enabled BOOLEAN NOT NULL DEFAULT FALSE,

  email VARCHAR(100) NULL,

  dingtalk_unionid VARCHAR(128) NULL UNIQUE,
  dingtalk_corp_id VARCHAR(128) NULL,
  dingtalk_userid VARCHAR(128) NULL,
  dingtalk_nick VARCHAR(100) NULL,
  dingtalk_bound_at TIMESTAMP NULL,

  must_change_password BOOLEAN NOT NULL DEFAULT FALSE,
```

字段解释说明
`id - Logtool 内部用户主键。业务数据、角色、权限都关联它`
`username -  Logtool 内部唯一用户名，钉钉用户登入后自动生成`
`dingtalk_unionid - 钉钉身份绑定标识，已有唯一约束`
`dingtalk_userid - 用户在某一个钉钉企业组织内的员工 ID。它只在对应企业内有意义，需要与 dingtalk_corp_id 一起使用`
`dingtalk_nick - 是钉钉返回的显示名称：免登场景通常是姓名，扫码场景可能是昵称。它只用于展示，不用于身份判断
`dingtalk_corp_id - 钉钉企业组织 ID。建议新增，并对 (dingtalk_corp_id, dingtalk_userid) 建立联合唯一约束`
`is_active - 账户是否为激活状态`
`password_hash - 本地密码，原先的账户管理方式是必填的，如果改为只支持钉钉登入，必须允许为空`
`must_change_password - 根据是否满足密码强度要求，确定是不是需要修改密码，钉钉用户固定为 false 即可`
`local_login_enabled - 默认 false，仅指定的应急超级管理员允许密码登录`
`scope_id - 暂未启用`
