# 日志自然语言搜索优化
目前批量日志查看页面通过前端给到后端数据库检索的是以下这些条件，自然语言搜索的只负责输出filters/actions/meta，不影响其他条件，那么自然语言搜索就是需要借助`LLM`的能力，将用户的自然语言解析为结构化文本称作`DSL`，后端再按照特定的规则解析未可以用作检索的`Where`表达式；调用LLM的方式改为 LLM补全对话的标准api，通过使用response_format来规范LLM的输出， 在 system prompt 中定义 DSL 输出结构，后端再对结果按 JSON Schema 校验
```
  - log_ids //日志id
  - search //关键词检索
  - error_code //故障码检索
  - start_time
  - end_time
  - filters //复杂的检索式
  - analysis_category_ids  //故障分类
  - include_ungraded  //是否包含未分类的
  - page  
  - limit
  - ids_only
```

定义`dsl`
```JSON
 {
    "filters": {
      "type": "group",
      "logic": "AND",
      "children": []
    },
    "actions": [],
    "meta": {
      "status": "ok",
      "explain": "",
      "questions": []
    }
  }
```
返回的JSON分为三个主节点字段分别为filter、action、meta,对于复杂检索条件、需要执行的动作、交互内容；

**filters**
其中filters用来表示复杂的检索，是一段用来表示根组逻辑的JSON
type：支持的值有group、condition
        - group 逻辑组，用来填写需要通过逻辑符号组合起来的条件组；
        - condition 叶子节点（所有判断都在这）,表达一个“一个具体条件”
一个 group 节点只能有一套type、 logic、children
children：是group逻辑组的内容列表children里装的是这个group逻辑组下面的子节点
logic：支持的值有 AND、OR ，表达逻辑组合之间是"与"还是“或”的关系
field：是用来表示需要约束的变量，支持的值有：timestamp（时间戳）、error_code（故障码）、参param1 / param2 / param3 / param4（参数1、参数2、参数3、参数4）、explanation（释义）；
op ：是用来表示运算符的， 
	对于field = timestamp 时支持 =、>、>=、<、<=、between
	对于field = error_code 时支持 =、!=、 contains、startswith、endswith、 notcontains
	对于field = param1 / param2 / param3 / param4 时支持 =、!=、>、>=、<、<=、between
	对于field = explanation 时支持 contains
value： 表示这个条件要拿来和 field比较的目标值
``` JSON
  {
    "type": "group",
    "logic": "AND",
    "children": [
      { "...": "条件1" },
      { "...": "条件2" }
    ]
  }
  
{
    "type": "condition",
    "field": "timestamp",
    "op": "between",
    "value": ["2026-07-06 10:00:00", "2026-07-06 11:00:00"]
}
```

`type` 支持`mark，stats`
- `mark` 表示使用特定的颜色标记标记日志条目，目前就支持默认的4种颜色，颜色和现有的颜色标记功能一致`color`支持 `yellow、purple、green、blue`若需要标记不支持的颜色`yellow`作为默认值；`{ "type": "mark", "field": "error_code", "value": "0x431D”, "color": "yellow" }` `field` 只支持 `error_code` 字段，`value`支持故障类型码或完整的故障码
- `stats` 表示用来统计特定故障码出现的次数；`field` 只支持 `error_code` 字段，`value`支持故障类型码或完整的故障码`{ "type": "stats", "field": "error_code", "value": "0x431D”` 不额外参与筛选，表示“对指定故障码进行出现次数统计”

meta
  - `status` 仅支持 `ok、need_clarification、fallback`
	  `ok` 表示已经完成DSL形式的返回，不需要追问，可以执行检索
	  `need_clarification`表示不执行检索，需要追问，澄清需要检索的对象；
	  `fallback` 表示语义无法判断，提示用户建议换检索方式；
  - `explain` 由`LLM`返回，填写用来解释本次解析的结果
  - `max_rounds` 最多追问的轮次，默认就是1；
  - `round` 用来记录当前追问的轮次
  - `max_rounds`和`round`由后端维护，`max_rounds`通过配置参数设置，默认为1，这两个字段不要求LLM返回，所以给到LLM的
  - `questions` `LLM`追问的内容，用`slot`和`question`两个字段表示
	  `slot` 表示缺少的字段，
		`scope` 缺少检索的对象
		`time_range` 缺少检索时间的范围
		`value_range` 缺少检索参数的取值范围
		`keyword` 缺少检索释义的关键词
		`question` 用来填充追问的问题
	  追问满足以下要求第一轮原始问题会保留
	  上一轮结构化结果会以 assistant message 回传
	  补问回答会作为新的 user message 追加
	  然后再让模型输出最终 DSL 或 fallback
    示例：
```JSON
    "meta": {
      "status": "need_clarification",
      "explain": "当前仍缺少更明确的检索范围",
      "max_rounds": 1,
      "round": 1,
      "questions": [
	      {
      	      "slot":"scope",
		      "question":"你想查哪一类异常，例如故障码、关键词"
	      }
      ]
    }
```

## filters
其中filters用来表示复杂的检索，是一段用来表示根组逻辑的JSON
type：支持的值有group、condition
        - group 逻辑组，用来填写需要通过逻辑符号组合起来的条件组；

value： 表示这个条件要拿来和 field比较的目标值
其中故障码规则：完整故障码通常由子系统ID（1位）+ 臂号（1位） + 关节号（1位） + 故障类型码（4位）组成，最后一位代表故障等级，A高优先级、B中优先级、C低优先级、D提示信息类型、E日志记录类，例如 141010A，
error_code允许填入完整故障码或4位的故障类型码，当用户输入的是完整的故障码op运算符通常使用"=、!="，用户输入的是故障类型码时op运算符通常使用"notcontains、contains、startswith、endswith"
param1 / param2 / param3 / param4参数1-4都是数字不会出现字母或文字，填入的value都应该是数值；
当前批次日志时间范围：{{logTimeRange}},今天的时间是{timedate}，只有用户明确限定了时间范围才填入timestamp的筛选内容，默认使用当前批次日志的时间范围；
因此示例中的filter部分表示检索，释义中包含“3号”，并且故障码包含050B或051B的日志条目
explanation contains "3号" AND (error_code contains "050B" OR error_code contains "051B")

# 优化运行数据存储和下载

运行数据上传后分为几类产物，并通过状态管理其上传、解析、异常等状态
	原始文件 bin：运行数据原始文件，作为唯一业务真相
	派生文件 csv：面向用户下载的导出格式
	派生文件 jsonl.gz：面向后端可视化、预览、分析扩展的结构化格式
	只提供解析后的csv下载和bin原始数据的下载；jsonl.gz做持久化但不提供下载；
	存储逻辑保持不变根据设置的模型确定是存入OSS还是本地；
	文件状态最终会停留在`completed、file_error、processing_failed` 三种状态之一，那么这三种状态都可以被删除，删除时派生文件和原始文件都会删除
	每一种类型的文件有的单独的状态管理，
		主状态：`uploading / parsing / completed / file_error / processing_failed`
		csv 状态：`pending / generating / ready / failed`
		jsonl 状态：`pending / generating / ready / failed`
		当 bin 正在上传时，主状态为 uploading，此时子状态为 pending
		当 bin 上传完成，任一子状态为 pending 或 generating 时，主状态为 parsing
		当 bin 文件校验失败时，主状态为 file_error
		当任一子状态为 failed 时，主状态为 processing_failed
		仅当 csv=json ready 且 jsonl=ready 时，主状态为 completed
```
主状态语义定义
	主状态 uploading仅表示原始 bin 文件上传中、落盘中，尚未进入解析
	主状态 parsing表示 bin 已上传成功，系统正在解析 bin，并生成 csv/jsonl.gz 等派生产物
	主状态 file_error表示 bin 文件本身存在问题，例如文件名、大小、帧结构、时间戳不合法
	主状态 processing_failed表示 bin 本身可用，但解析或派生文件生成过程中出现异常
	主状态 completed仅当 csv 和 jsonl.gz 子状态都为 ready 时，主状态才为 completed
子状态语义建议定义为：
	pending尚未开始生成
	generating正在生成
	ready已生成完成，可被使用
	failed生成失败
```

## 利用大语言模型的编排与构建 `LLM Orchestrator & Extractor`
- 对于提示词构建应该分为几个部分， #contextenvelope 主要用来管理用户的会话历史上下文， #contextTool 主要用来构建工具部分的prompt；

	- user部分包含用户的输入和上下文；
	- tool部分包含可以使用的现有工具与摘要；
	- memory暂时未填写；
- prompt根据系统语言区分中文和英文；
- prompt按照配置的方式实现，prompt调用 #LLM 得到意图和事实澄清的结果，规范 #LLM 填写一个结构化的数据 [[多轮会话涉及的结构化数据#意图识别结果| #ContexIntent]]，意图识别的结果需要转化映射到 [[多轮会话涉及的结构化数据#写入消息的中间映射层| #ConversationMessageInput]] 做标准化，然后通过message service存入 #conversation_messages 表，这部分仅用于记录原生的 #LLM 的返回内容；以role = assistant 写入数据表 

## 工具网关`Tools Gateway`

- 整体上：**声明 → 加载 → 教模型认识工具 → 校验入参 → 网关编排 →（HTTP 或进程内）执行**，上层 Planner 只产出「是否调用、调用谁、参数草稿」，不穿透到具体存储细节。
	- 工具声明注册用[[工具注册标准模板（Registry）]]描述工具名称、启用开关、`inputContract、outputContract、llmSummary、权限与安全元数据` 作为工具能力的唯一声明来源；
	- 加载与解析，读取 `registry/v1/index.json` 及下属工具文件，归一化槽位字段（`requiredSlots` / `anyOfRequired` / `optionalSlots`），构建按名索引与 intent → 规范名的映射。
	- 意图 Prompt 绑定，将当前启用工具折叠为意图模型的可读说明（**`description`、槽位、`properties`**）；**不包含** `llmSummary.whenToUse`（快捷命令另行用于预处理）；约束 LLM 输出的 `toolName` 落在合法集合内。
	-  参数校验，在执行前依据 registry 的 `inputContract` 校验必填与 `anyOfRequired`、注入 `defaultable`、校验 `enum`/`pattern`，非法输入在进入 Handler 前即失败并带上明确错误码。
	- 工具网关，承接 Planner 的 `call_tool` 决策（`invokeByPlan`），串联校验、执行适配（进程内 Handler **或** HTTP 客户端）、异常与超时处理，并把输出规范为 `ToolResult` 矩阵与调试元数据。
	- 执行适配，进程内：直接调本仓库服务层；HTTP：按 Registry 中的端点与映射构造请求、解析响应；二者都对网关暴露相同的「原始返回值」形态，不直连会话状态机
- 在构建工具的prompt时，首先通过index索引文件，建立获取对应的工具注册表，形成prompt
- 
```
  你不能直接调用工具，只能判断是否需要调用工具，并补充调用时需要的输入参数，输入参数的规则
	- `requiredSlots` 每项必填；空数组表示无单独必填；
	- `optionalSlots` 可选择的输入参数，非必须
	- `anyOfRequired` 每组至少填其中一个槽位即通过校验，使用`，`分割"slotA", "slotB"
	- `properties`  配置了 enum → 取值必须在枚举里，配置了 pattern → 必须匹配该正则，没有填或为空的参数不会走这一段，string → 取值可以为字符串；
	  可以使用的工工具：
	  {toolName}，用途：{description}
		{
		
		"requiredSlots": [],
        "optionalSlots": [],
        "anyOfRequired": [],
        "missingSlotQuestions"
        "properties": {}
        }
```
  

## 规划层 Planner  
- 需要根据 #ContextIntent 、上下文、工具权限、整体策略构建 #planInputContext 
	- 其中 requestMate 需要根据会话确定traceId、requestId、sessionId、turnId；
	- contextIntent 根据 校验过后的内容 直接映射；
	- contextSummary 根据本次会话构建时的 #contextenvelope 一一映射；
	- availableTools 里放“已注册工具 + 该工具所需权限/约束”；
		- name工具名称、enabled是否启用、requiredPermission需要的权限、allowed（基于当前用户权限计算）
		- requiredSlots 需要的输入参数，不同的工具需要有不同的输入内容；
		- runtimeState 运行状态字段
			- userPermissions 来自鉴权结果；再按工具相关权限做裁剪
			-  remainingCalls 工具调用预算剩余次数
			-  resetAt 限流/配额窗口重置时间
		- policy字段
			- maxSteps单次计划最多允许多少个步骤。
			- maxToolCalls单次计划最多允许调用多少次工具。
			- timeoutBudgetMs单次计划可消耗的总时间预算（毫秒），超出就降级。
			- clarifyRoundLimit最多允许连续追问用户几轮，超过后应改为其他处理（如给保守答复或结束本轮）。

- 每一轮会话开始时，打印一次系统提示词system、用户提示词user、工具提示词tool、记忆提示词，有使用注入方式遇到无内容填充null；
需要记录user的问题、
- 用户的问题包含：当前的问题：ContextEnvelope.currentInput.rawtext; 是否包含附件通过attachments字段判断是否有附件，只需要显示 是或否；历史对话总结：ContextEnvelope.historyContext，最近轮次的内容ContextEnvelope.recentTurns；已经确认的内容ContextEnvelope.confirmedSlots
- LLM回答的包含：识别到的意图：intent，下一步行为：nextAction.type和对应的提示信息：nextAction.type，回答内容：answerDraft
- 工具执行完成后的内容：结果状态：status，内容：data；
- 系统返回的错误和异常；
- 增量记录，按照消息触发逐条记录，而不是按照会话把会话内容全记录；

### 故障码检索
- 支持完整故障码检索，完整故障码是 1XY010A这种形式，优先通过前缀匹配拼接出完整故障码的子系统号、臂号、关节号，拼接逻辑参考故障码释义中的方式；
- 支持故障码类型的短码，类似0X010A/010A这种形式，如果是短码需要用户确认子系统号；
- 支持关键词搜索，不超过20个字，召回返回最多10个
- handler（errorCodeLookupHandler）里的文本是它自己拼出来的，分 3 种：
  • 无结果：t('errorCodeLookup.notFound')
  • 单条命中：toLookupText(...) 生成一段说明，内容会包含，
    • foundPrefix（查询到的故障码）
    • hintInfo（前缀+userHint+operation），前缀+给用户的提示信息+操作信息
    • paramMeaning（param1~4），参数解释
    • detail / detectLogic / techSolution / category（有值才拼），详细信息，检测方法，排查方案，故障类型
  • 多条命中：buildLookupTextMulti(...) 生成“命中多条”的列表（按 subsystem + code），并且和单条命中一致，返回 
    • foundPrefix（查询到的故障码）
    • hintInfo（前缀+userHint+operation），给用户的提示信息+操作信息
    • paramMeaning（param1~4），参数解释
    • detail / detectLogic / techSolution / category（有值才拼），详细信息，检测方法，排查方案，故障类型
